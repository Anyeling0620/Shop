### 3.2 依赖关系一句话总结

- **最底层（不依赖任何服务）**：`goods-service`、`user-service`
- **中间层（依赖别人）**：`order-service` → goods + user；`seckill-service` → goods；`search-service` → goods
- **只写不调**：`canal-service`（只发 MQ，不调任何服务）
- **纯消费**：`search-service` 消费 MQ
- **基础设施**：`eureka-server`（被所有服务依赖）、`gateway`（依赖路由目标服务）

**启动顺序必须遵守这个拓扑**：Eureka → gateway → goods/user → order/seckill → search → canal → web-app。

### 4.3 一个重要的架构问题：跨库 JOIN

`SeckillGoodsDao` 的 SQL 是：

```sql
select g.id as goods_id, g.name, ..., gs.price_seckill, gs.stock_seckill
from goods_seckill gs left join goods g on gs.goods_id = g.id
```

**没有库名前缀**。而 `seckill-service` 的数据源连的是 `seckill` 库，所以它要求 **`seckill` 库里也有一张 `goods` 表** —— 这就是 `seckill.goods` 存在的原因（内容确认是 `goods.goods` 的 2 行拷贝：id=1 华为Mate X2、id=2 华为Mate40Pro）。

**这是典型的分库禁忌**：同一个业务实体在两个库里存了两份，靠人工同步维持一致。一旦 `goods.goods` 改了名/改了价，`seckill` 库里的副本不会变，秒杀页显示的就是旧数据。

两种正规改法：
1. **改 SQL 加库名**：`left join goods.goods g on gs.goods_id = g.id`（同实例跨库，最省事）
2. **不 JOIN**：只查 `goods_seckill`，商品信息走 `Feign goodsApi.get()`（最符合微服务边界，代码里 `checkGoodsOnSale()` 已经在这么做了，等于查了两次）

## 五、秒杀服务有没有做「分库」和「热点隔离」？

**直接回答：分库没有做，热点隔离做了一半（缓存层有，数据库层没有）。**

### 5.1 分库：❌ 完全没做

| 检查项 | 结果 |
|---|---|
| 依赖里有没有分片中间件 | ❌ 无。`seckill-service/pom.xml` 只有 `mybatis` / `mysql-connector` / `druid` / `redis` / `amqp`，没有 ShardingSphere、Sharding-JDBC、dynamic-datasource |
| 数据源数量 | ❌ **1 个**。`application.yml` 里只有一条 `spring.datasource.url`（`seckill` 库） |
| 有没有分片键 / 分片规则 | ❌ 无。所有 SQL 都是单表/跨库 JOIN，没有取模、没有 `user_id % N` |
| 有没有多数据源路由 | ❌ 无 `AbstractRoutingDataSource` 实现 |

**关键事实**：`goods_seckill`、`order`、`order_seckill` 三张表都是**单库单表**，`order_seckill` 靠 `UNIQUE KEY uk_user_goods(user_id, goods_id)` 保证一人一单 —— 这个唯一索引在**单库单表**下有效，一旦真的分库，这个约束就失效了（跨库全局唯一必须靠分布式锁/号段）。

> 代码里唯一和「分」沾边的是 `GoodsService` 的注释：「使用雪花算法生成**分库分表**唯一 id」。但那是 `goods` 模块生成商品 ID 用的，**只是预留了 ID 方案，并没有真的分库**。

### 5.2 热点隔离：⚠️ 部分做了，全在缓存/应用层，DB 层裸奔

要说「热点隔离」，得分层看。秒杀确实是热点中的热点，做法如下：

| 层次 | 有没有隔离 | 具体做法 | 评价 |
|---|---|---|---|
| **入口层** | ✅ 有 | 网关 `RequestRateLimiter` 令牌桶（`replenishRate=1`, `burstCapacity=5`），按 IP 限流 | 但**只配在 goods 路由上**，seckill 路由没配限流！ |
| **应用层** | ✅ 有 | `seckillOverMap`（JVM 本地 `ConcurrentHashMap`）记录「已售罄」，命中即返回，不碰 Redis | 多实例不一致，只能算半隔离 |
| **缓存层（Redis）** | ✅ 有 | `seckill:stock:{goodsId}` 原子 `DECR` 预减，把库存判断从 MySQL 挪到内存 | **这是最关键的一层，做对了** |
| **防刷** | ✅ 有 | 动态 `path`（MD5 随机串，60s 有效） | 属于接口防刷，不是热点隔离 |
| **削峰** | ✅ 有 | RabbitMQ `seckill.queue` 异步落库，请求不阻塞 | 有效 |
| **数据库层** | ❌ **没有** | 所有秒杀订单都写同一张 `order` 表、同一张 `order_seckill`，单库单表 | **这是最大的缺口** |
| **热点数据本地缓存** | ❌ 无 | 没有 Caffeine/Guava 本地缓存秒杀商品信息 | 每次 `detail` 都可能打到 DB |

### 5.3 实测证据：防超卖已经漏了

查真实数据发现：

```sql
select goods_id, stock_seckill from seckill.goods_seckill;
-- goods_id=1 -> stock_seckill = 9
-- goods_id=2 -> stock_seckill = -70     ← 库存负了 70!

select goods_id, count(*) from seckill.order_seckill group by goods_id;
-- goods_id=1 -> 1 单
-- goods_id=2 -> 198 单   但配置的库存远小于 198
```

`stock_seckill = -70` 说明**数据库里已经存在超卖脏数据**（198 单 vs 配置库存已扣到 -70）。
**注意**：单靠现有数据无法反推确切成因 —— 可能是早期版本没有 `stock_seckill > 0` 这个守卫，也可能是测试期手工改库造成的。但无论哪种，都说明这份数据没有经过并发压测验证。

当前代码里的守卫是：

```sql
update goods_seckill set stock_seckill = stock_seckill - 1
where goods_id = #{goodsId} and stock_seckill > 0
```

`stock_seckill > 0` 这个条件是**对的**，且在 `@Transactional` 内执行、影响行数为 0 就抛异常回滚。所以**当前这一版在 DB 层是能防住超卖的**；-70 是历史遗留，需要手工修数据把负数补回 0（否则 `@PostConstruct` 预热时会把 -70 写进 Redis，导致该商品永远秒不到）。

**顺带一个真 bug**：`SeckillController.doSeckill()` 里 `stock < 0` 时做了：

```java
redisService.set(SECKILL_GOODS_OVER + goodsId, "true");   // 永久无货标记
redisService.incr(SECKILL_STOCK + goodsId);               // 回补
```

`goodsOver` 标记**没有 TTL，也没人删**。一旦某商品被误判无货，**即使补货也不会恢复**（只能重启服务重建缓存）。这和 P2 里「预热只跑一次」是同一个病根。

### 5.4 如果真要做热点隔离，该怎么做

按投入产出排：

1. **给 seckill 路由加限流**（1 行配置，最紧急）
   ```yaml
   - id: zhuawa_shop_seckill_route
     filters:
       - StripPrefix=1
       - name: RequestRateLimiter
         args:
           key-resolver: "#{@ipKeyResolver}"
           redis-rate-limiter.replenishRate: 5
           redis-rate-limiter.burstCapacity: 20
   ```

2. **修 `goodsOver` 标记**：加 TTL（如 1 小时），或补货时主动 `delete`。

3. **数据库层做水平拆分**（真正的「分库」）：`order_seckill` 按 `user_id` 取模分表，热点商品单独走独立库/独立表（bitmap 或活动维度分表）。这才叫热点隔离。

4. **热点商品本地缓存**：把 `seckill:goods:{id}` 放进 Caffeine，加 Redis pub/sub 广播失效。

5. **MQ 队列隔离**：现在所有秒杀商品共用 `seckill.queue`，热点商品会堵死冷门商品。可以按商品维度拆多个队列，或多消费者并行。
