# 爪哇商城（zhuawa-shop）架构分析与快速上手指南

> 本文基于当前仓库代码（`HEAD = 4d3cfbb`）与本机实际环境实测得出，所有结论都能对应到具体文件或命令。
> 与已有的《项目剖析-上手指南.md》相比，本文修正了已过期的结论，并补充了「本机环境实测」与「启动级坑位」。

---

## 0. 一句话结论

这是一个 **Spring Cloud 教学型电商单体拆微服务** 项目：9 个可独立启动的 Spring Boot 服务 + 1 个注册中心 + 1 个网关，用 **Eureka 做服务发现、Gateway 做统一入口、OpenFeign 做服务间调用、RabbitMQ 做异步削峰、Canal 做数据库变更捕获、ES 做搜索**。核心看点是 **秒杀链路**（Redis 预减库存 + MQ 异步下单 + 数据库条件更新三重防超卖）。

## 1. 模块全景（15 个 Maven 模块 / 133 个 Java 文件）

| 模块 | 端口 | 角色 | 关键内容 |
|---|---|---|---|
| `eureka-server` | 8761 | 注册中心 | `@EnableEurekaServer`，不注册自己 |
| `gateway` | 8081 | **统一入口** | 4 条路由 + `AuthFilter` JWT 鉴权 + Redis 令牌桶限流 + CORS |
| `web-app` | 18004 | 静态前端 | 8 个 html（`login/goods_detail/cart_list/seckill/...`），jQuery + Bootstrap，**无后端逻辑**，但启动类带了 `@EnableEurekaClient` |
| `goods-service` | 18001 | 商品服务 | 商品/品牌/类目/规格，MySQL `goods` 库；含「按规格递归生成模拟商品」 |
| `order-service` | 18002 | 订单服务 | 购物车 + 下单，MySQL `order` 库；**Feign 调 goods 扣库存 + user 加积分** |
| `user-service` | 18006 | 用户服务 | 登录发 JWT、MD5 加盐、积分，MySQL `user` 库 |
| `seckill-service` | 18007 | **秒杀服务（核心）** | Redis 预减 + RabbitMQ 异步下单 + 事务防超卖，MySQL `seckill` 库 |
| `search-service` | 18003 | 搜索服务 | Spring Data ES，消费 MQ 同步商品到索引 |
| `canal-service` | 18005 | 数据同步 | 监听 `goods.goods` 的 binlog → 发 RabbitMQ |
| `canal-starter` | — | **自研 starter** | 把 Canal 客户端封装成 `@EnableCanalClient` / `@CanalEventListener` / `@ListenPoint` |
| `common` | — | 公共 jar | `Result` / `CodeMsg` / `JwtUtil` / `AccessInterceptor` / `UserContext` / `IdWorker` / `GlobalExceptionHandler` |
| `goods-service-client` | — | **API 契约包** | `GoodsApi`（`@FeignClient("goods")`）+ 6 个 POJO |
| `user-service-client` | — | API 契约包 | `UserApi`（`addPoint`） |
| `seckill-service-client` | — | API 契约包 | `SeckillApi`（`result/query`） |

**依赖方向**：

```
common ← goods-service-client ← goods-service
   ↑            ↑                order-service / search-service / seckill-service
   └────────────┴── user-service-client ← order-service / user-service
                  └── seckill-service-client ← seckill-service
gateway 不依赖 common（WebFlux 栈冲突），自带一份 JwtUtil
```

> 拆 `*-service-client` 的原因：调用方不能依赖可执行 jar（会把对方的依赖和配置一起拖进来），只能依赖「接口 + POJO」的契约包。

## 2. 架构图与一次请求的完整链路

```
                    浏览器（页面托管在 :18004 web-app）
                              │  所有 AJAX 都打 http://localhost:8081
                              ▼
                  ┌───────────────────────────────┐
                  │  Gateway :8081 (WebFlux/Netty) │
                  │  ① 路由匹配 Path=/xxx/**       │
                  │  ② AuthFilter 校验 JWT         │
                  │  ③ Redis 令牌桶限流（仅 goods）│
                  │  ④ StripPrefix=1               │
                  └───────┬───────────────────────┘
                          │ uri: goods/user 写死 IP；order/seckill 用 lb://
        ┌─────────────────┼──────────────┬───────────────┐
        ▼                 ▼              ▼               ▼
   goods :18001     user :18006    order :18002    seckill :18007
        │                 ▲              │  Feign ────────┤ Feign
        │                 └──────────────┘               │
        ▼                                                ▼
   MySQL goods 库                              MySQL seckill 库
        │ binlog                                    Redis / RabbitMQ
        ▼
  canal-service :18005 ──MQ(canal.queue)──▶ search-service :18003 ──▶ Elasticsearch
                                                   ▲
                                                   └── Feign 反查 goods 拿最新数据

   所有服务 ──注册/心跳──▶ Eureka :8761
```

**以秒杀为例，请求走完全程**：

1. 前端 `seckill.html` → `GET http://localhost:8081/seckill/seckill/list`
2. 网关匹配 `Path=/seckill/**` → `StripPrefix=1` 吃掉第一个 `seckill` → 目标路径 `/seckill/list`
   → `AuthFilter` 从 header/cookie/query 取 `zhuawa-shop-token`，`JwtUtil.parseJWT` 验签
   → `lb://seckill` 去 Eureka 查实例 → 转发 `http://ip:18007/seckill/list`
3. `seckill-service` 的 `AccessInterceptor.preHandle()`：解析 JWT → `LoginUser` 塞 `ThreadLocal`（`UserContext`）→ 校验 `@AccessLimit`
4. `UserArgumentResolver` 把 ThreadLocal 里的 `LoginUser` 直接注入 Controller 参数
5. `afterCompletion()` → `UserContext.clear()`（防线程池串号）
6. 返回 `Result{code,msg,data}`

> **`StripPrefix=1` 的语义**：网关吃掉路径第一段。所以前端基址是 `http://localhost:8081/seckill/seckill`（重复的 `seckill` 看着别扭但是对的：第一个是路由前缀，第二个是服务内 `@RequestMapping`）。

## 3. 秒杀核心链路（最值得读的部分）

面对「瞬时高 QPS vs 库存只有几十件」，设计是**层层拦截，把绝大多数请求挡在数据库之前**：

```
请求 10000 QPS
   │ ① 网关限流（令牌桶 1/s，桶容量 5）      → 挡掉突发
   │ ② 秒杀 path 校验（MD5 随机串，60s）      → 挡掉脚本直接拼 URL
   │ ③ 内存标记 seckillOverMap               → 已售罄直接返回，连 Redis 都不访问
   │ ④ Redis DECR 原子预减库存               → 把库存判断从 MySQL 挪到内存
   │ ⑤ Redis SETNX 一人一单                 → 防重复下单
   │ ⑥ 发 MQ 立刻返回 0（排队中）            → 削峰，请求不阻塞
   ▼
只剩 ≈ 库存数量 的消息进入 seckill.queue
   │ ⑦ 消费者 @RabbitListener 串行落库
   │    @Transactional：UPDATE ... WHERE stock_seckill > 0 兜底
   ▼
MySQL 真实扣减（最后一道闸）
```

**代码位置**：`seckill-service/.../controller/SeckillController.java`、`service/SeckillOrderService.java`、`rabbitmq/MQReceiver.java`、`dao/SeckillGoodsDao.java`

**防超卖三重保障**：

| 层 | 手段 | 作用 |
|---|---|---|
| Redis | `DECR` 原子预减（`stock < 0` 则回补 + 打无货标记） | 把 99% 并发挡在 MQ 之前 |
| MQ | `seckill.queue` 单队列串行消费（`concurrency: 10`、`prefetch: 1`） | 把并发写变成可控的串行写 |
| MySQL | `UPDATE goods_seckill SET stock_seckill = stock_seckill - 1 WHERE goods_id = ? AND stock_seckill > 0`，影响行数 0 就抛异常回滚 | 绝对兜底，前面全失效也不会扣成负数 |

**结果查询约定**（`GET /seckill/result/{goodsId}`）：`orderId > 0` 成功 / `-1` 失败（无货）/ `0` 排队中。
查询顺序：Redis 结果缓存 → MySQL 兜底 → 看 `goodsOver` 标记。

**幂等三处**：`order_seckill` 表的 `uk_user_goods` 唯一索引、消费前先查是否已下单、Redis `SETNX` 标记。

## 4. 数据同步链路：MySQL → ES

```
goods 表 INSERT/UPDATE/DELETE
        │  （Canal 伪装成 MySQL slave 读 binlog）
        ▼
canal-service :18005
   MysqlListener（@CanalEventListener + @ListenPoint 声明监听 goods.goods）
        │  只取 id 和事件类型，封装 CanalMessage{schema, table, primaryKey, operationType}
        ▼
RabbitMQ canal.queue
        ▼
search-service :18003
   MQReceiver（@RabbitListener）
        │  DELETE → es.deleteById
        │  其他   → 调 goodsApi.get(id) 拿最新商品 → es.save
        ▼
Elasticsearch 索引 goods_es_info（mapping: search-service/resources/mapping/goods_es_info.json）
```

**设计要点**：Canal 只负责「通知哪条数据变了」，真正的数据由 `search-service` 反查 `goods-service` 拿**最新完整数据**。既避免了解析 binlog 字段的复杂度，也避免消费到旧消息。

`canal-starter` 是一个标准 starter 写法（`spring.factories` + `@ConfigurationProperties` + `@ConditionalOnProperty`），想学「怎么写自己的 starter」看这个模块最合适。

### 5.2 数据库准备：**这里是最大的启动坑**

仓库里 `sql/` 只有这些表的 DDL：

- `brand` / `category` / `category_brand` / `specs` / `param` / `template`（`goods_table.sql`，**未带库名**，需先 `CREATE DATABASE goods`）
- `order.cart_item` / `order.orders` / `order.order_item`（`order_table.sql`）
- `user.user`（`user_table.sql`）
- `docs/秒杀建表.sql`：`seckill.goods_seckill` / `seckill.order` / `seckill.order_seckill`（这份是后来补的）

**❗ 缺失：`goods.goods` 表本身没有 DDL。** 代码里 `GoodsDao`、`GoodsController.get()`、`SeckillGoodsDao` 的 JOIN 全都依赖它。
可以让 `goods-service` 启动后调 `GET /goods/genMockGoods?baseName=华为手机&categoryId=1&brandId=1&minPrice=1000&maxPrice=9000&stock=100` 来生成商品数据 —— 但**前提是这张表已经存在**。所以必须自己补建表语句（可参照 `Goods.java` 字段反推）：

```sql
CREATE DATABASE IF NOT EXISTS `goods` DEFAULT CHARSET utf8mb4;
USE `goods`;
CREATE TABLE `goods` (
  `id`            bigint       NOT NULL,
  `name`          varchar(255) NOT NULL DEFAULT '',
  `price`         bigint       NOT NULL DEFAULT 0,
  `stock`         bigint       NOT NULL DEFAULT 0,
  `image`         varchar(511) NOT NULL DEFAULT '',
  `brand_id`      bigint       NOT NULL DEFAULT 0,
  `category_id`   bigint       NOT NULL DEFAULT 0,
  `brand_name`    varchar(127) NOT NULL DEFAULT '',
  `category_name` varchar(127) NOT NULL DEFAULT '',
  `param_json`    varchar(2047) NOT NULL DEFAULT '',
  `specs_json`    varchar(2047) NOT NULL DEFAULT '',
  `status`        int          NOT NULL DEFAULT 0 COMMENT '0=上架',
  `create_time`   datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`   datetime     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (`id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

> `sql/goods_data.sql` 只灌 `brand/category/category_brand` 三张表的数据；`sql/goods_tmp_data.sql` 是另一套 `tb_*` 表的数据，**和本项目表结构对不上，不要灌**。

另外 `SeckillGoodsDao` 的 SQL 是 `from goods_seckill gs left join goods g ...`，**没有库名前缀** —— 在 `seckill` 库里执行，要求 `seckill` 库也能访问 `goods` 表。二选一：
- 改 SQL 加库名：`left join goods.goods g on gs.goods_id = g.id`（推荐）
- 或 `CREATE TABLE seckill.goods LIKE goods.goods;` 再同步数据

## 6. 上手时会立刻踩到的坑（按严重度排序）

### P0 · 直接起不来 / 功能必挂

1. **`goods.goods` 表缺 DDL** —— 见 §5.2，必须先补。
2. **JDK 版本不匹配** —— 本机只有 JDK 21，Spring Boot 2.5.4 跑不动（见 §5.1）。
3. **`seckill-service` 启动即查库** —— `SeckillController` 上的 `@PostConstruct init()` 会立刻查 `goods_seckill` 并把库存预热进 Redis。**表不存在或 JOIN 失败 → Bean 初始化失败 → 整个服务起不来**。
4. **`gateway` 路由把 goods/user 写死成 IP**：
   ```yaml
   - id: zhuawa_shop_goods_route
     uri: http://localhost:18001   # ← 绕过 Eureka，无法多实例负载均衡
   - id: zhuawa_shop_user_route
     uri: http://localhost:18006   # ← 同样问题
   - id: zhuawa_shop_order_route
     uri: lb://order               # ← 正确写法
   ```
   建议统一改成 `lb://goods` / `lb://user`。

### P1 · 能跑但有设计缺陷

5. **`AuthFilter` 里 mutate 了 request 但没重建 exchange**：
   ```java
   request.mutate().header(COOKIE_NAME_TOKEN, token);  // 结果被丢弃
   return chain.filter(exchange);                       // 传的还是原 exchange
   ```
   应为 `chain.filter(exchange.mutate().request(request.mutate().header(...).build()).build())`。
6. **未登录跳转地址指向网关自身**：`loginURL = "http://localhost:8081/login.html"`，但 8081 不托管静态页（静态页在 18004），未登录会 403 跳到一个 404。应改 `http://localhost:18004/login.html`。
7. **登录接口返回的是 UUID 而不是 JWT**：
   ```java
   String token = UUIDUtil.uuid();   // 生成后没用上
   addCookie(response, user);        // cookie 里放的是正确的 JWT
   return token;                     // 却把 UUID 返回给前端
   ```
   前端若把返回值当 token 用，鉴权必失败（好在 `seckill.html` 是从 cookie 里读 token 的）。
8. **没有任何熔断/降级**：依赖里零熔断组件（已确认所有 yml 里连 `feign.hystrix.enabled` 都已被移除）。Feign 默认读超时 60s，下游卡住会拖垮线程池。要做得加 `spring-cloud-starter-circuitbreaker-resilience4j` 或 Sentinel。
9. **网关只配了 4 条路由**（goods/user/order/seckill），而 `search_goods.js` 直接打 `http://127.0.0.1:18003/search` **绕过网关**，且 8081 的 CORS 白名单是 `http://localhost:18004` —— 换端口访问就会跨域失败。

### P2 · 高并发/运行期问题

10. **秒杀失败后 `orderMark` 不清理**：`SETNX` 的 TTL 是 3600s，但「库存不足 / path 非法 / 重复」时都没 `delete`，用户失败一次要等 1 小时才能重试。
11. **`seckillOverMap` 是 JVM 本地 Map**：多实例下不一致（不会超卖，Redis 兜底，但「减少 Redis 访问」失效；补货必须重启才清标记）。
12. **库存预热只在 `@PostConstruct` 跑一次**：运行期新增秒杀商品 / 补货，Redis 里是旧值。
13. **Redis 预减成功但 MQ 发送/消费失败 → 少卖**：需要定时对账（Redis 剩余 + DB 已售 = 总量）或失败回补。
14. **`order-service.genOrder` 没有分布式事务**：Feign 扣库存 → 插 `order_item` → Feign 加积分 → 删购物车 → 插 `orders`，中间任一步失败前面都回不去（代码里留了 `//TODO if distributed transaction necessary?`）。

### P3 · 整洁度

15. **`common` 太重**：塞了 `spring-boot-starter-web` + thymeleaf + knife4j，导致 WebFlux 栈的 `gateway` 不能复用它，只能复制一份 `JwtUtil`（`user-service` 里还有第三份）。建议拆 `common-core`（零 web 依赖）+ `common-web`。
16. **JWT 密钥硬编码 `1a2b3c4d` 且三处拷贝**。
17. **`mapper-locations: classpath:mapper/*Mapper.xml` 指向空目录**：全项目零 Mapper XML，DAO 全是注解 / tk.mybatis，这行是历史残留。
18. **`WebConfig` 上用 `@SpringBootConfiguration`**：语义上应该是 `@Configuration`。
19. **秒杀订单与订单服务是两套表**（`seckill.order` vs `order.orders`），真实业务应合并。

## 8. 常见修改场景对照表

| 我想… | 改哪里 |
|---|---|
| 加一个接口 | `XxxController` → `XxxService` → `XxxDao`（注解 SQL 或 `Mapper<T>`，**不需要 XML**） |
| 加一张表 | 建 `model/Xxx.java`（驼峰对应下划线，`map-underscore-to-camel-case: true` 已开）→ `dao/XxxDao extends Mapper<Xxx>` |
| 服务间加调用 | ① client 模块加 `@FeignClient` 接口 ② 调用方 pom 引入 ③ 调用方启动类 `@EnableFeignClients` 加包名 |
| 加网关路由 | `gateway/application.yml` → `routes`，用 `lb://服务名` |
