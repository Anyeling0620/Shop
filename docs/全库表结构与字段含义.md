### 5.2 `seckill.goods_seckill` — 秒杀活动配置表（2 行）★核心

> 归属：**seckill-service**（`SeckillGoodsDao.listSeckillGoods/getByGoodsId/reduceStock/countOnSale`）
> 这是**秒杀活动的业务主表**：库存扣减、时间控制、价格都在这

| 字段 | 类型 | 允许空 | 默认值 | 键 | 含义与代码用途 |
|---|---|---|---|---|---|
| `id` | bigint unsigned | NO | — | **PK** | 配置 ID，自增 |
| `goods_id` | bigint unsigned | NO | 0 | **UNI(联合)** | 关联 `seckill.goods.id`（不是 goods 库！）。JOIN 时 `gs.goods_id = g.id` |
| `session_id` | int unsigned | NO | 0 | **UNI(联合)** | **场次编号**（新增）。同一商品可开多场，`(goods_id, session_id)` 唯一定位一场。存量数据统一回填 0，即「0 号场」 |
| `price_seckill` | decimal(10,2) | NO | 0.00 | | **秒杀价**，单位元。当前两件都配 1.00 |
| `stock_seckill` | int | NO | 0 | | **秒杀库存**（可负数的 int！）。`reduceStock` 用 `where stock_seckill > 0` 防超卖。⚠️ 当前 `goods_id=2` 已为 **-70** 脏数据 |
| `start_time` | datetime | YES | NULL | | 秒杀开始时间。`seckillStatus()` 判断 `now < startAt` → 状态 0 未开始 |
| `end_time` | datetime | YES | NULL | | 秒杀结束时间。`now > endAt` → 状态 2 已结束 |
| `create_time` | datetime | NO | CURRENT_TIMESTAMP | | 创建时间 |
| `update_time` | datetime | NO | CURRENT_TIMESTAMP | | 更新时间 |

**索引**：`PRIMARY(id)`、`uk_goods_session **UNIQUE(goods_id, session_id)**`

> **场次改造说明（迁移脚本：`sql/seckill_session_migration.sql`）**
> - 改造前 `goods_id` **没有唯一索引**，同一商品可配多条秒杀、只靠自增 `id` 区分，无法表达「第几场」。
> - 现在 `UNIQUE(goods_id, session_id)` 让「某商品的某一场」成为数据库层面的唯一事实：同一商品的同一场次不可能配两行，否则 `reduceStock` 会命中多行、扣多份库存。
> - `session_id` 之所以是 `NOT NULL DEFAULT 0` 而不是可空：MySQL 唯一索引对 NULL 不去重，多行 NULL 会让唯一约束形同虚设。
> - 场次编号只要求「同一商品内唯一」，不要求全局连续，各商品可以各排各的。
> - **代码侧**：`SeckillGoodsDao.getByGoodsId()` 按 `session_id desc limit 1` 取「当前场次」（对只有 0 号场的存量数据与改造前等价）；需要精确到某一场时必须用 `getByGoodsIdAndSession(goodsId, sessionId)`；`reduceStock` 已改为按 `(goods_id, session_id)` 扣减。

### 5.4 `seckill.order_seckill` — 秒杀订单索引表（199 行）★一人一单兜底

> 归属：**seckill-service**（`OrderDao.insertOrderSeckill/getOrderSeckill`）
> 作用：**「一人一单」的数据库层最后一道防线**

| 字段 | 类型 | 允许空 | 默认值 | 键 | 含义与代码用途 |
|---|---|---|---|---|---|
| `id` | bigint unsigned | NO | — | **PK** | 主键，自增 |
| `order_id` | bigint unsigned | NO | 0 | | 关联 `seckill.order.id` |
| `user_id` | bigint unsigned | NO | 0 | **UNI(联合)** | 用户 ID |
| `goods_id` | bigint unsigned | NO | 0 | **UNI(联合)** | 商品 ID |
| `session_id` | int unsigned | NO | 0 | **UNI(联合)** | **场次编号**（新增），对应 `goods_seckill.session_id`。历史订单统一回填 0 |
| `create_time` | datetime | NO | CURRENT_TIMESTAMP | | 创建时间 |
| `update_time` | datetime | NO | CURRENT_TIMESTAMP | | 更新时间 |

**索引**：`PRIMARY(id)`、`uk_user_goods_session **UNIQUE(user_id, goods_id, session_id)**`、~~`user_goods UNIQUE(user_id, goods_id)`~~（**已删除**）

> **「一人一单」粒度改造说明（迁移脚本：`sql/seckill_session_migration.sql`）**
> - 旧约束 `UNIQUE(user_id, goods_id)` 的语义是「同一用户同一商品**永远**只能下一单」——商品开第二场时，老用户会被数据库直接挡死，秒杀永远抢不了。
> - 新约束 `UNIQUE(user_id, goods_id, session_id)` 把粒度降到**场次级**：同一场次内只能一单，**跨场次可以再抢**。
> - **必须先建新索引、再删旧索引**，不能反过来：先删后建会出现一个没有任何唯一约束保护的窗口，并发下单可能插入重复行，之后再建唯一索引会直接失败。
> - 旧索引**不保留**做历史兼容：唯一索引是强约束、无法只对某一场生效，只要它还在，本次改造就完全失效。而「历史订单仍可查」由数据本身保证（行还在），不依赖该索引。
> - 原索引顺带提供的 `user_id + goods_id` 查询前缀支持，已由新索引的最左前缀覆盖，`OrderDao.getOrderSeckill` 无需额外普通索引。
> - **代码侧**：`OrderDao.getOrderSeckill / insertOrderSeckill`、`MQReceiver` 的幂等判断、`SeckillOrderService.createOrder` 均改为带 `session_id`。

## 七、必须知道的三个「坑」（字段层面的不一致）

### 坑 1：两套商品表，两套 ID 体系

| 对比项 | `goods.goods` | `seckill.goods` |
|---|---|---|
| ID 生成 | **雪花算法**（1432247757988474880 起） | **自增**（1、2） |
| 价格单位 | `bigint`，**分** | `decimal(10,2)`，**元** |
| 图片字段 | `image` | `img` |
| 状态字段 | 有 `status`（0 正常/1 下架） | **无 status** |
| 行数 | 15110（规格化 SKU） | 2（独立商品） |

**实测验证**：`goods_seckill.goods_id = 1/2` 在 `goods.goods` 里**查不到**（因为 goods 表 id 都是雪花 ID）。
所以 `SeckillOrderService.checkGoodsOnSale()` **不能** Feign 调 goods-service 校验 —— 这正是我本次修掉的 bug（改为查本地 `goods_seckill inner join goods`）。

### 坑 2：两套订单表，字段名不同

| 概念 | `order.orders` | `seckill.order` |
|---|---|---|
| 收货地址 | `receive_address` | `delivery_address` |
| 商品价 | `total_price`(分, 汇总) | `goods_price`(元, 单品) |
| 状态码 | 0-5（含「已评价」） | 0-6（含「退款中/已退款」） |
| 数量 | 在 `order_item.count` | `goods_count` |

**两者互不相通**：秒杀订单不会进 `order.orders`，查「我的订单」也查不到秒杀订单。

### 坑 3：全库没有外键，全靠「逻辑外键」

`information_schema.key_column_usage` 查询结果：**零外键约束**。
所有 `xxx_id` 都是逻辑关联，一致性靠代码保证。这符合微服务「数据库私有」原则，但**也意味着脏数据不会被数据库拦下来**（比如 `order_item.goods_id` 指向一个不存在的商品）。
